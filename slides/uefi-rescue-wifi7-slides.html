Dynamic Handles vs. Absolute Paths

UEFI filesystem handles (FS0:, FS1:) and Linux block nodes (/dev/sda, /dev/sdb) are ephemeral enumeration artifacts. Only UEFI Device Paths and partition UUIDs are stable.

Handle renumbering scenarios:

  • FS0:/FS1: typically = internal firmware volumes (Fv(...)), not storage media
  • A rescue thumbdrive may be FS4: NVMe-attached, but shift to FS0: if you remove storage drives
  • hard-coding FS4: → FS2: without re-verification overwrites unintended partitions

The shell navigation protocol:

Shell> map -r          # re-enumerate all handles
Shell> map -fs            # show only filesystems
Shell> fs4:                 # enter the handle
FS4:\> ls \EFI\BOOT        # verify contents before executing

# Never assume FS4 persists across reboots or hardware changes

Decoupling the Five-Layer Boot Pipeline

The Jetson boot is a relay across five independent execution environments. You cannot resolve a failure at one layer by manipulating a different layer.

1Hardware & BootROM (read-only memory)—FORCE_RECOVERY_N strap (J14), APX (Application Processor) 0955:7020
▼
2QSPI (quad serial peripheral interface) UEFI (Unified Extensible Firmware Interface), TianoCore EDK II, NVRAM (non-volatile memory) variable quarantine (Slot A/B retry threshold)
▼
3ESP (Extensible Firmware Interface System Partition) Bootloader—BOOTAA64.EFI → extlinux.conf → grubaa64.efi
▼
4Linux Kernel—EFI stub, console=ttyTCU0, DTB (device tree blob)
▼
5OS Userspace—systemd, network, display manager
Diagnostic rule: Identify the highest layer that produces output (serial, USB enumeration, EFI shell, kernel log). Higher layers stay suspect. Lower layers are ruled out. Each layer has its own failure signature.

GUID Drift and Silent Boot Invalidation

UEFI NVRAM boot entries bind to partition unique GUIDs (PARTUUID) rather than partition indices or device names. When an OS installer regenerates the GPT partition table, existing boot entries silently point to nothing —firmware skips them without error and falls through to PXE (Preboot Execution Environment) or Shell>.

Detection (3 steps)

  1. Inspect live partition GUID: map -r—note GUID in HD(n,GPT,<GUID>,...)
  2. Compare against NVRAM: bcfg boot dump
  3. Check for mismatch—firmware falls through silently

Correction

  • Launch bootloader directly: fsN:\EFI\BOOT\BOOTAA64.EFI
  • Re-register with current GUID: bcfg boot add
  • Linux equivalent: efibootmgr with new PARTUUID

Signaling Channels: Display ≠ System State

A blank screen or flashing cursor does not prove boot failure. On Jetson, kernel command-line arguments (console=ttyTCU0, fbcon=map:0, video=efifb:off) direct output to the serial port and disable the EFI framebuffer. The kernel boots normally while the monitor stays dark.

Non-visual diagnostic ladder:

  1. Physical link: Check Ethernet switch LEDs → arp -an / ping <ip>—distinguish powered-down vs. unbootable
  2. Fleet SSH: ssh root@<ip>—if SSH connects, userspace is live
  3. VT (virtual terminal) switch: Ctrl+Alt+F2–F6—spawn text getty, bypassing crashed graphics
  4. Serial console: Micro-USB/J14 UART (Universal Asynchronous Receiver-Transmitter) (ttyTCU0, 115200 8N1)—unbuffered hardware output from BootROM through kernel

Principles 6 & 7: Identity vs. Silicon, and Emulation Limits

6. Board Identity: Paperwork ≠ Silicon

Jetson identity is the COMPATIBLE_SPEC string in /etc/nv_boot_control.conf and the TegraPlatformCompatSpec variable. I2C (Inter-Integrated Circuit) EEPROM (electrically erasable programmable read-only memory) read timeouts during flashing cause fallback to wrong strings (Orin NX on Orin Nano Super), breaking nvidia-l4t-bootloader upgrades.

Correction (no SPI re-flashing needed):

  1. Fix /etc/nv_boot_control.conf to match hardware
  2. dpkg --configure -a or run the post-install script
  3. Script syncs corrected string to efivarfs automatically

7. The Asymmetric Validity Rule

Replicated faithfully:

  • GPT layout (Primary + Backup LBAs)
  • FAT32 structures & BPB alignment
  • GRUB 2.12 syntax & module search

Zero evidence for:

  • PCIe link training
  • L4TLauncher probe behavior
  • Dynamic handle shifts
  • Ext4Dxe filesystem compatibility
A failure in QEMU diagnoses hardware. A success in QEMU proves the media only. Never deploy rescue media to remote fleets without a physical validation boot.
